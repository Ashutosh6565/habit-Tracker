1. Executive summary

Habbiters is a well-structured habit-tracking application with a genuinely solid security foundation on the backend: ownership scoping prevents cross-user data access (no IDOR), input is globally sanitised, auth routes are rate-limited, one-time passwords and refresh tokens are stored hashed, passwords use bcrypt at cost 12, and the Stripe webhook verifies its signature against the raw request body. Those are the hard things to get right, and they are right.

The review nonetheless surfaced one critical issue, several high-severity issues, and a broad tail of medium and low items. Two themes dominate. First, the entire premium / paywall / billing system has been deliberately switched off in code — not via configuration, but by commenting out real logic and returning hard-coded “everyone is premium” stubs across both backend and frontend. This looks intentional (a “make everything free” decision), but it was done in a way that leaves dead, misleading code throughout the codebase and needs a clean resolution. Second, a handful of real defects exist independent of that decision: JWTs stored in localStorage (the critical item), an avatar-upload path that trusts client-supplied file types, an N+1 query explosion in streak calculation, and two build-breaking type errors on the frontend.

None of the security-relevant findings require a rewrite. The recommended sequence in §5 fixes the critical and high items in small, low-risk steps, starting with the auth fix that is already applied.

4. The dominant theme: the paywall is disabled in code

Across both tiers of the application, the logic that would gate premium features has been replaced with stubs that grant everything, and the real implementations have been left in place but commented out. This is consistent enough to look like a deliberate “make the whole app free” decision — but because it was done by editing code rather than by a feature flag, the codebase now contains a large amount of dead, contradictory logic. Where it currently lives:

LocationCurrent behaviour
services/subscription.service.tsgetSubscriptionTier() does void subscription; return "premium"; the real tier logic is commented out. formatSubscription() hard-codes isPremium:true, status:"active", isActive:true.
config/permissions.tshabits.unlimited, templates.premium, analytics.advanced, reports.export each have their original free:false commented out and replaced with free:true.
services/habit.service.tscreate() — the free-plan 5-habit limit block is fully commented out.
controllers/payment.controller.tscheckout returns a fake { id:"free-access", url:null }; cancelSubscription is a no-op. Real Stripe calls are commented out.
Frontend gatesPremiumGate renders children unconditionally; ProtectedRoute only blocks when a permission is explicitly false; Templates treats every template as accessible; Pricing hard-codes the current tier to free.
Decision needed before any “fix.” If free-for-everyone is the intended product, the clean path is to remove the dead billing/subscription/permission code (and the Stripe surface) rather than leave it commented — otherwise every future reader has to reverse-engineer which branch is live. If the paywall is meant to come back, it should be reinstated behind a single feature flag. Either way this is a product call, so nothing in this area was changed in this pass.

5. Detailed findings

5.1 Critical

SEC-1  JWTs stored in localStorageCRITICAL

frontend/src/lib/api.ts — tokenStore
What Both the access token and the long-lived refresh token are persisted with localStorage.setItem and read back on every request to build the Authorization header.
Why it matters localStorage is readable by any JavaScript running on the page. A single XSS vector — a dependency compromise, an unescaped user string, a malicious avatar (see SEC-2) — lets an attacker exfiltrate both tokens and fully impersonate the user, including refreshing sessions indefinitely. This is the highest-impact issue in the codebase.
Fix Move tokens to httpOnly, Secure, SameSite cookies set by the backend (the backend already reads req.cookies?.accessToken, so it is half-wired for this). The frontend then stops touching token storage entirely and relies on credentials:"include" (already set). If tokens must remain client-side short-term, at minimum keep only the access token in memory (not localStorage) and keep the refresh token in an httpOnly cookie.

5.2 High

AUTH-1  Unhandled rejection in auth middlewareFIXED IN THIS PASS

backend/src/middlewares/auth.middleware.ts — authenticate
What authenticate was async but registered directly (not through asyncHandler). verifyAccessToken() calls jwt.verify, which throws on an expired, malformed, or tampered token. In an async handler that throw becomes a rejected promise with no .catch.
Why it matters Access tokens expire every 15 minutes, so this fired routinely: instead of a clean 401, the request produced an unhandled promise rejection and hung. That also broke the frontend’s refresh-on-401 flow (it never received the 401 that triggers a refresh), and unhandled rejections can crash the Node process under strict settings.
Fix applied Wrapped authenticate (and the structurally identical requirePermission) with the existing asyncHandler, and wrapped the verifyAccessToken call in try/catch that maps token errors to a 401 INVALID_TOKEN — preserving the client refresh flow. Full diff in §7.

SEC-2  Avatar upload trusts client-supplied typeHIGH

backend/src/middlewares/upload.middleware.ts + app.ts static /uploads
What The multer fileFilter checks file.mimetype (sent by the client and trivially spoofed) and the stored filename’s extension comes from path.extname(file.originalname) (also client-controlled). Files are then served as static content from /uploads.
Why it matters An attacker can upload an .html or SVG payload with a declared image MIME type; when the victim opens the served URL, it executes in the app’s origin — stored XSS, which chains directly into SEC-1 to steal tokens.
Fix Validate real content by sniffing magic bytes (e.g. file-type) rather than trusting the header; generate the stored filename and extension server-side from the detected type (never from originalname); serve uploads with Content-Type pinned and Content-Disposition: attachment (or from a separate cookieless domain), and add a restrictive CSP.

PERF-1  N+1 explosion in streak calculationHIGH

backend/src/services/habit.service.ts — getCurrentStreak / formatHabit
What getCurrentStreak loops up to 365 times, awaiting a separate HabitProgress.findOne each iteration. formatHabit calls it for every habit, and list() / summary() call formatHabit for every habit via Promise.all.
Why it matters A user with 20 habits triggers up to ~7,300 sequential database round-trips for a single page load (~36,600 at 100 habits). This dominates latency and will fall over under any real concurrency.
Fix Replace the per-day loop with one range query per habit (fetch the last N days of HabitProgress in a single call and compute the streak in memory), or aggregate all habits’ recent progress in one $in / aggregation query and derive every streak from that result set.

BUILD-1 / BUILD-2  Frontend type-check failsHIGH

frontend/src/pages/Analytics.tsx (~L385) · frontend/src/pages/Home.tsx (~L193)
What tsc reports two errors: a Recharts Legend formatter whose signature does not match the expected type, and a reference to plan.period on a type that has no period field.
Why it matters These break a strict production build (tsc / vite build). They are small but block CI and any type-safe deploy.
Fix Give the formatter the signature Recharts expects ((value, entry, index) => ReactNode) or cast the callback; correct the plan object shape (add period to the type or read the field that actually exists).

5.3 Medium

DATA-1  Filter applied after paginationMEDIUM

backend/src/services/habit.service.ts — list()
What The DB query paginates with skip/limit on a filter that excludes completed (a derived field), and total = countDocuments(filter) also ignores it. The completed filter is then applied to the already-paginated page in memory.
Why it matters A “show completed” view returns only whatever happens to be on the current page, and the pagination meta (total, totalPages) is wrong whenever that filter is used.
Fix Push completion state into the query (join/lookup against today’s HabitProgress, or precompute a per-day completion set) so filtering and counting both happen at the database before skip/limit.

AUTH-2  No single-flight guard on token refreshMEDIUM

frontend/src/lib/api.ts — request() 401 branch
What When several requests receive 401 at once, each independently posts to /auth/refresh. With refresh-token rotation, the first rotates the token and the rest present a now-stale token, fail, and call tokenStore.clear().
Why it matters A burst of parallel calls (a dashboard loading several widgets) can spuriously log the user out.
Fix Share a single in-flight refresh promise: the first 401 starts the refresh, concurrent callers await the same promise, then all retry once.

DATA-2 / UX-1 / UX-2 / STREAK-2  State & correctnessMEDIUM

DATA-2 Sign-out does not reset the in-memory habit context, so a subsequent login on the same tab can briefly show the previous user’s habits. Clear all client state on logout.
UX-1 The dashboard weekly chart is populated with Math.random() rather than real completion history. Wire it to the summary/analytics endpoint.
UX-2 Analytics reads only from in-memory context, so a hard refresh shows a blank page until data is re-fetched. Fetch on mount.
STREAK-2 The streak loop starts at i=0 (today); if today is not yet completed it breaks immediately and reports 0, hiding an otherwise-active streak. Start from yesterday (or treat today as optional) when computing the streak.

5.4 Low (roll-up)

Individually minor; worth a cleanup sweep once the above are resolved:

  • Dead / contradictory code from the disabled paywall (see §4) — largest single source of confusion.
  • setProgress sets completedAt: undefined in a $set, which does not clear a previous completedAt (use $unset).
  • Notification sentAt is set even when the send did not actually occur.
  • Outbound email HTML is not escaped (header/footer injection risk in templated mail).
  • YouTube metadata fetch has no timeout (a slow upstream can hang the request).
  • avatarUrl accepts arbitrary schemes (no http(s)-only restriction).
  • Admin user list is returned un-paginated.
  • Frontend .env is not git-ignored; secrets/URLs risk being committed.
  • 404 page and footer use raw <a> tags instead of the router, causing full reloads.
  • Assorted dead code / unused exports left after the stubbing.
  • Fallback dev secrets in env.ts are convenient but should be impossible to use if NODE_ENV is ever misconfigured — fail fast outside development too.
  • Weekly/monthly stats and level thresholds are magic numbers; centralise them.
Confirmed correct — do not “fix.” Ownership scoping (no IDOR), route auth wiring, global Mongo sanitisation, rate limiting on auth routes, hashed OTP with attempt limits, hashed refresh tokens, bcrypt cost 12, Stripe webhook signature verified against the raw body, cascade delete of HabitProgress, sensible indexes/unique constraints, and request body-size caps are all implemented correctly.

7. Changes applied in this pass

File: backend/src/middlewares/auth.middleware.ts — fixes AUTH-1 (and the same latent defect in requirePermission).

+ import { verifyAccessToken, type AccessPayload } from "../utils/tokens";
+ import { asyncHandler } from "./asyncHandler";

- export const authenticate = async (req, _res, next) => {
-   const payload = verifyAccessToken(token);   // throws on expired token
+ export const authenticate = asyncHandler(async (req, _res, next) => {
+   let payload: AccessPayload;
+   try {
+     payload = verifyAccessToken(token);
+   } catch {
+     return next(new AppError("Invalid or expired token", 401, "INVALID_TOKEN"));
+   }
    ...
+ });   // wrapped so any async rejection is forwarded to next()

- export const requirePermission = (permission) => async (req, _res, next) => { ... };
+ export const requirePermission = (permission) =>
+   asyncHandler(async (req, _res, next) => { ... });

Rationale: reuse the codebase’s existing asyncHandler pattern, and map token-verification failures to 401 so the frontend refresh-on-401 flow continues to work. Verification via tsc/eslint/tests is pending re-running the toolchain (shell unavailable this session); the change is type-safe by construction and confined to one file.

8. Phased remediation plan

Phase 0 — Done in this pass

AUTH-1: auth-middleware unhandled rejection fixed; starter test suite + npm test added. Next action for you: run cd backend && npm test and npm run lint to confirm green on your machine.

Phase 1 — Security (do next)

SEC-1 (move JWTs out of localStorage into httpOnly cookies) and SEC-2 (validate upload by magic bytes, server-side filename, safe serving). These two together close the account-takeover chain.

Phase 2 — Build & correctness

BUILD-1/BUILD-2 (unblock the frontend type-check), DATA-1 (filter before pagination), AUTH-2 (single-flight refresh), STREAK-2 (streak off-by-one).

Phase 3 — Performance

PERF-1 (replace the streak N+1 with range/aggregate queries). Highest user-visible latency win.

Phase 4 — Product decision & cleanup

PAY-0: decide free-for-everyone vs. reinstating the paywall, then either delete the dead billing/permission code or reintroduce it behind one feature flag. Fold in the §5.4 low-severity cleanups (DATA-2, UX-1/UX-2, email escaping, timeouts, .env ignore, router links).

Appendix — running the tests. Backend: cd backend && npm test (compiles to dist/, then runs node --test tests/; use npm run test:only to skip the rebuild). Frontend: cd frontend && npm run test (Vitest). Both suites are dependency-free beyond what the project already installs. Sandbox caveat: this environment mounts Windows node_modules into Linux and blocks the npm registry, so vitest/tsx and any install cannot run here — they work normally on your machine.
